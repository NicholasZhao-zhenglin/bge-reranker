## 项目目标与背景

先在本地运行 `bge-reranker-v2-m3`，理解 reranker 的输入、输出和推理过程，为后续 LoRA 微调建立基线。

## 当前架构与关键模块

- 模型类型：XLM-RoBERTa encoder-only sequence classification reranker。
- 输入：一个 query 和一个 passage，作为文本对一起输入。
- 输出：一个相关性 logit；经过 sigmoid 后可得到 0 到 1 之间的可读分数。

## 问题、失败尝试与解决方案

### 2026-07-11｜相对路径导致本地模型被误判为远程模型

- 症状：在 `D:\\bge_reranker\\scripts` 目录执行脚本时，Transformers 报告 `models/bge-reranker-v2-m3` 不是本地目录，并尝试访问 Hugging Face，最终出现 `401 Unauthorized`。
- 根因：相对路径是相对于当前工作目录解析的，不是相对于 Python 脚本文件解析的；从 `scripts` 目录启动时，实际查找的是 `scripts/models/bge-reranker-v2-m3`。
- 解决：使用 `Path(__file__).resolve().parents[1]` 定位项目根目录；对本地模型使用绝对路径，并设置 `local_files_only=True`。
- 可迁移经验：命令行、PyCharm 和 IDE 的 working directory 可能不同；依赖项目文件的路径应显式基于项目根目录解析，不能只依赖当前目录。

### 2026-07-11｜步骤：原始 reranker 基线与错误模式

- 目标：在微调前用固定测试集量化原始模型表现，并从真实排序结果定位可学习的错误。
- 做了什么：对 60 条合成测试 query 的 480 个 query-passage 候选对进行批量推理，保存逐 query 排名、分数、指标和错误案例。
- 观察到的事实：Recall@1 为 0.833333，Recall@3 为 0.983333，Recall@5 为 1.0，MRR 为 0.898611；出现 10 个 Top-1 误排和 3 个低间隔风险。
- 为什么这样做：LoRA 的目标应由可观察的失败模式决定，而不是先训练再寻找理由。
- 考虑过的替代方案及取舍：可以只看总指标，但总指标无法说明模型为什么错；因此额外保存了逐候选 raw score 和 metadata。
- 遇到的问题/失败尝试：无；基线模型成功使用 GPU 对全部 480 个文本对打分。
- 如何验证：检查 `baseline_rankings.jsonl` 中 gold rank，独立计算 Recall@k 和 MRR。
- 结论：主要错误是型号混淆，其次是同部件不同任务类型的混淆；应构造对应 hard negative。
- 我应该学会：重排序改进的核心不是“多喂一些负样本”，而是让负样本刻意接近模型当前会犯的错误边界。

### 2026-07-11｜步骤：从误排结果挖掘难负样本

- 目标：把模型真实犯错的候选文本转化为下一轮 LoRA 数据，而不是凭直觉随机采样负样本。
- 做了什么：从 10 个 Top-1 误排和 3 个低间隔风险中提取 query、正确 chunk、误排 chunk、分数、错误类型和元数据，生成 13 条可追溯 hard negative。
- 观察到的事实：9 条样本属于“同一部件、同一任务类型、型号不同”的混淆；1 条属于“同一部件、任务类型不同”的混淆；3 条是正确但分数间隔过小的风险样本。
- 为什么这样做：这些负样本位于模型当前的决策边界附近，通常比随机无关文本更能帮助模型学会区分型号和任务意图。
- 考虑过的替代方案及取舍：可以把所有测试候选都加入训练，但这样会混入大量简单样本并造成测试泄漏；本次只保留失败和低间隔案例，并单独隔离。
- 遇到的问题/失败尝试：无；已在输出中加入数据泄漏警告。
- 如何验证：检查每条 hard negative 都能关联到 `evaluation_id`、正负 chunk ID、原始分数和错误类别。
- 结论：下一轮 LoRA 优先补充型号区分和“验收/故障”意图区分的样本。
- 我应该学会：hard negative 的价值在于“足够像正确答案但仍然错误”，而不在于数量大。

### 2026-07-11｜问题修复：训练负样本跨 split 泄漏

- 症状：最终审查发现初版数据生成器为训练样本挑选负样本时使用了全量文档池，因此训练样本可能包含测试文档作为负例。
- 根因：数据划分只约束了正样本来源，`select_negatives` 没有接收当前 split 的候选池。
- 修复：训练、验证、测试样本分别只从所属 split 的文档中挑选负例；仅最终评测候选池可以从全库抽取干扰文档，以模拟真实检索库。
- 防回归：数据验证脚本新增断言，检查每条训练样本的所有负例与正例处于同一 split。
- 结论：数据切分必须同时约束正例和负例；否则即便不把测试文档标为正例，也会造成内容泄漏。

## 可迁移经验与面试表达

### 诚实的项目表达

我构建了一个面向设备运维问答的 RAG reranker 实验闭环。先将领域文档切成可追溯 chunk，构造 query/正样本/普通负样本数据，并冻结测试候选池；随后用原始 BGE reranker 建立 Recall@k 和 MRR 基线，保存逐样本排名。错误分析显示模型主要混淆同一部件的不同设备型号，因此从真实误排中挖掘型号相近的 hard negative，作为下一轮 LoRA 的针对性训练候选。为避免数据泄漏，我没有把测试误排样本直接混入原测试集的训练与评测闭环。

### 可能追问

1. 为什么不直接随机采样负样本？因为随机负样本过于简单，无法有效纠正模型在相似候选之间的真实边界错误。
2. 为什么不能把测试误排直接加入训练后再报告指标？这样测试集信息已经泄漏到训练中，提升无法代表泛化能力。
3. Recall@5 为何高但 Recall@1 较低？说明正确文档通常被召回到候选池，但最终精排序仍会被相近型号或相近任务的文本抢占第一名。
4. LoRA 数据优先补什么？同部件不同型号、同型号不同任务类型，以及参数值相近但设备型号不同的对比样本。

## 可迁移经验与面试表达

### 面试表达初稿

我先使用 Transformers 直接加载本地的 BGE reranker 模型，输入 query 和 passage 文本对。模型不是分别生成两个向量再计算距离，而是通过 encoder 对文本对进行联合编码，最后由分类头输出一个相关性 logit。我同时保留原始 logit 和 sigmoid 后的分数，前者便于保留模型原始输出，后者更容易解释。随后我会用相关和不相关的 passage 做成对对比，建立微调前的排序基线。

### 2026-07-11｜步骤：对比相关与不相关文本

- 实验设置：固定 query `什么是LoRA微调？`，分别输入相关 passage 和无关 passage。
- 相关 passage：`LoRA是一种参数高效微调方法，只训练少量低秩适配器参数。`
- 相关结果：raw score `6.175781`，sigmoid score `0.997925`。
- 无关 passage：`北京今天天气不错`。
- 无关结果：raw score `-11.039062`，sigmoid score `0.000016`。
- 结论：在这组样例中，模型能够将相关文本排在无关文本之前；reranker 的核心用途是比较同一个 query 下多个 passage 的相关性分数。
- 性能观察：两次延迟分别为约 `170.85ms` 和 `559.25ms`，延迟会受 GPU 预热、显存状态、系统负载和 CUDA 调度影响，不能用相关性分数解释。
- 可迁移经验：判断排序模型是否有效，优先做控制变量实验——固定 query，只替换候选文本，再比较模型分数和排序结果。

### 2026-07-13｜实验：C-MTEB T2Reranking LoRA 单 epoch 训练

- 目标：在本机 RTX 4060 Laptop 8GB 上完整体验一次 reranker LoRA 微调，并监测 Loss、吞吐、内存、显存和温度。
- 数据：过滤无正样本或无负样本的无效 query 后，固定划分为 4000 条训练、1000 条验证、908 条测试；本轮训练集展开为 66,214 个 query-passage pair。
- 配置：`bge-reranker-v2-m3`，LoRA `r=8`、`alpha=16`、`dropout=0.1`，目标模块为 `query/key/value`；`batch_size=8`、梯度累积 2、有效 batch 16、最大长度 256、1 epoch，共 4,139 个优化 step。
- 预检：batch 4 + 梯度检查点的首次 smoke test 在梯度缩放阶段出现 `Attempting to unscale FP16 gradients`；根因是 LoRA 可训练参数仍为 FP16。将可训练参数转换为 FP32 并加入回归测试后恢复正常。
- 批量选择：batch 8、梯度累积 2、关闭梯度检查点时峰值 PyTorch 显存约 2.82GB，速度优于 batch 16，因此正式训练采用该配置并保留显存余量。
- 训练结果：完整 epoch 耗时约 25.19 分钟，吞吐约 43.81 pair/s；前期 Loss 均值 0.899236，近期均值 0.567661，相对下降 36.87%，最终 batch Loss 0.563576。
- 资源监测：训练时系统显存占用约 3.9GB，系统内存约 68%–70%，GPU 利用率多为 93%–98%，温度多为 75–82°C；未发生 OOM、NaN/Inf、持续 Loss 发散或资源阈值告警。
- 验证结果：MRR 0.830018，Hit@1 0.724，Hit@3 0.922，Hit@5 0.972，Hit@10 0.995；nDCG@1 0.724，nDCG@3 0.700590，nDCG@5 0.710757，nDCG@10 0.772629。
- 产物：LoRA adapter 与 tokenizer 保存于 `outputs/c-mteb-lora-epoch1/adapter`，训练事件与汇总分别保存为 `training_metrics.jsonl` 和 `training_summary.json`；模型产物由 `.gitignore` 排除，不提交到 Git。
- 评估边界：上述数值来自验证集，不能与先前 908 条测试集 baseline 直接计算提升。验证集用于选择 epoch 和超参数；模型选择完成后，才在冻结测试集上做一次最终前后对比。
- 结论：当前配置能在本机稳定完成单 epoch LoRA 训练，Loss 有明确下降，资源仍有安全余量；是否真正改善泛化排序能力，需要同一测试集上的微调前后指标才能确认。

### 2026-07-13｜验证：冻结测试集上的 LoRA 前后对比

- 目标：加载单 epoch LoRA adapter，在与原始 baseline 完全相同的 908 条冻结测试集上判断泛化排序能力是否提升。
- 做了什么：复用相同测试 JSONL、候选集合、指标函数、`batch_size=8` 和 `max_length=512`，仅将模型从基础权重替换为“基础权重 + LoRA adapter”；保存 LoRA 指标、逐 query 排名和自动差值报告。
- 观察到的事实：Hit@1 从 0.657489 提升到 0.751101（+0.093612，净增加 85 条 Top-1 命中）；MRR 从 0.791302 提升到 0.849389（+0.058087）；Hit@3 从 0.910793 提升到 0.940529；Hit@5 从 0.969163 提升到 0.980176；nDCG@10 从 0.738207 提升到 0.786299。Recall@1/3/5/10 与全部 nDCG 指标也均提升。
- 配对分析：151 条 query 从 Top-1 错误变为正确，66 条从正确变为错误，531 条始终正确，160 条始终错误；MRR 改善 214 条、变差 97 条、不变 597 条。对 151 比 66 的不一致样本做精确二项检验，双侧 `p=7.679e-09`。
- 为什么这样做：只有在同一个从未参与训练的测试集上控制推理配置，指标差值才能归因于 adapter；逐 query 配对还能揭示净提升背后的修正与回退。
- 考虑过的替代方案及取舍：可以将训练后验证集指标与测试 baseline 直接相减，但 split 不同会使结论失真；因此重新在冻结测试集推理。也可以只报告总分，但会掩盖 66 条 Top-1 回退。
- 遇到的问题/失败尝试：最初尝试使用 SciPy 计算精确检验，但环境未安装 `scipy`；没有为单个统计量修改环境，改用 Python 标准库 `math.comb` 计算精确二项概率。
- 如何验证：8 项单元测试通过；评估器强制检查测试 query 数与 baseline 一致，并拒绝不同的 `max_length`；完整评估覆盖 14,798 个候选 pair，结果写入 `outputs/c-mteb-lora-epoch1/test_evaluation`。
- 结论：本次单 epoch LoRA 微调在冻结测试集上产生了明确且具有统计证据的提升，尤其是 Top-1 和前几位排序质量；但仍应分析 66 条回退与 160 条持续错误，再决定是否训练第二个 epoch。
- 我应该学会：总指标提升不代表每个 query 都变好；模型迭代应同时查看净提升、配对修正/回退和错误类型，验证集负责选模型，测试集负责一次性报告泛化结果。

#### 面试表达与可能追问

我在固定的 C-MTEB 重排序数据上先建立原始 BGE baseline，再使用 4000 条 query 对模型进行单 epoch LoRA 微调。为保证前后可比，我冻结 908 条测试 query，并保持候选集、截断长度、batch 和指标代码不变。微调后 Hit@1 从 65.75% 提升到 75.11%，MRR 从 0.7913 提升到 0.8494；配对分析显示修正 151 条、回退 66 条，精确检验 `p<1e-8`。这说明轻量微调有效，但下一轮优化重点应是分析回退样本，而不是只看训练 Loss 继续增加 epoch。

1. 为什么 Hit@1 与 Recall@1 不相等？每个 query 可能有多个正样本；Hit@1 只问第一名是否任一正样本，Recall@1 衡量第一名覆盖了全部正样本中的多少比例。
2. 为什么不能拿验证集结果和测试 baseline 比？不同 query 集合的难度不同，差值同时混入数据差异，不能归因于微调。
3. 为什么报告修正 151 条和回退 66 条？净增 85 条不能展示副作用；配对计数能定位模型在哪些 query 上改善或退化。
4. 是否应该立刻再训练一个 epoch？不能只根据训练 Loss 决定；先查看验证集趋势和 66 条回退的类型，再决定继续训练、降低学习率或增加针对性 hard negative。
